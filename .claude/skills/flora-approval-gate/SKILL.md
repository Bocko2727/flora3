# Флора 3 — Approval Gate

Целта е две грешки да не се случват: необратимо действие без одобрение и излишно питане за обратимо. И двете губят доверие и време.

## 1. Определи нивото

| Ниво | Действия |
|---|---|
| **§5.1 Пълен блок** | secrets; пари, нов пакет, MCP сървър, connector, външна услуга; триене/презаписване на оригинални снимки или растения, `DROP`, масов `DELETE`/`UPDATE`; триене на облачен ресурс; **merge в `main`**, force-push, пренаписване на история; запис в стария Supabase (`sxuxtsbyqjaodyuqebux`) |
| **§5.2 Кратко** | миграция в хоста (`lfmkjxcaokndltdylama`); единична обратима промяна в production данни; настройки във Vercel (env, домейни, protection); Pl@ntNet пакет над 20 заявки |
| **§5.3 Свободно** | клонове `feat/fix/chore` (създаване, commit, push); PR (отваряне, обновяване); триене на влети клонове; CI файлове на клон; read-only scheduled tasks; Figma, artifacts, Project Knowledge; Pl@ntNet до 20 заявки; всичко само с четене |

При съмнение: по-високото ниво. Ако действие съчетава нива (напр. PR + миграция в хоста), разделяй: свободната част я правиш, за другата искаш одобрение.

Общи думи („давай“, „оправи всичко“) не са одобрение за §5.1/§5.2. Нужна е точната фраза за конкретния обхват. Одобрението важи за едно действие и не се пренася.

## 2. §5.3 — без блок

Направи го и го отчети накрая. **Не питай** за push и PR.

## 3. §5.2 — кратко (2–3 реда)

Първо всички проверки само с четене. После:

```text
**Нужно е кратко одобрение:** <какво, едно изречение>
Команда/SQL: `<точно>`
Rollback: `<точно>`
→ „Одобрявам: <кратко име>“
```

За миграция: файлът и pgTAP тестът са на клон и минават локално (`/new-migration`); никога `supabase db push`; прилага се с `apply_migration` или от собственика в SQL Editor. За Pl@ntNet: точен брой заявки и оставащата квота за деня.

## 4. §5.1 — пълен блок, после СПРИ

```text
## Нужно е действие от теб

### Какво ще направя
- [едно конкретно, ограничено действие]

### Точен обхват
- Repo/проект/клон: [...]
- Засегнати файлове/ресурси: [...]
- Точен diff, SQL, команда или payload: [...]

### Защо е нужно сега
- [...]

### Проверки след действието
- [...]

### Rollback
- [...]

### Гаранции
- main няма да бъде променен/merge-нат.
- Няма production deploy извън одобреното.
- Оригинални снимки и растения няма да бъдат изтрити/презаписани.
- Secrets няма да бъдат показвани или записвани в client код.

За да продължа, отговори точно: `Одобрявам: [кратко име на действието]`.
```

Ако собственикът трябва да действа сам в интерфейс (merge, secret в GitHub/Vercel), добави „Твоите стъпки в интерфейса“: 1–4 стъпки, какво да види и какво да върне — **без secrets**. Никога не искай secret в чата, screenshot или код.

Merge на PR е винаги стъпка на собственика; агентът никога не пуска `gh pr merge`. Блокът за merge е само „Твоите стъпки в интерфейса“: дай линка към PR-а и какво да провери (CI зелен, Vercel preview).

## 5. Примери

| Действие | Ниво |
|---|---|
| push на `feat/family-index`, отваряне на PR | §5.3 |
| `select count(*) from plants` | §5.3 |
| нова колона в хоста | §5.2 |
| решение за двете гъби в `/review` (един запис) | §5.2 |
| нова env променлива във Vercel | §5.2 |
| 30 заявки към Pl@ntNet | §5.2 |
| `npm install` на нов пакет, нов MCP сървър (Svelte MCP е одобрен и в `.mcp.json`; Playwright MCP чака) | §5.1 |
| merge на PR | §5.1 (стъпка на собственика) |
| триене на снимка от Storage | §5.1 |
| `git push --force` | §5.1 (и е блокирано в `.claude/settings.json`) |
